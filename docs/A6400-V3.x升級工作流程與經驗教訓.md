# Sony A6400 homebrew (V3.x CLite/Fast-SP) 本机升级：工作流程与经验教训

> **社群贡献者：阿杰**（同一台 Sony ILCE-6400 连续四次跨版本升级实战总结：V3.0 → V3.1 → V3.5.1 → V3.9）
> 适用机型：Sony ILCE-6400（A6400）固件 2.00；操作系统 Windows。
> 一句话结论：**升级本身不难，难在 Windows USB 驱动和作者脚本的上传逻辑——90% 的时间消耗在这两处。**

---

## 一、先看懂这套系统在做什么

理解机制能避免大量瞎试：

| 层 | 作用 | 位置 |
|---|---|---|
| **hook 程序** | 开机早期注入 UI、建立 constructor lock、触发启动脚本 | V3.0–V3.5.1：`/tmp/a6400-autoexec.so`；**V3.9 起：`/etc/a6400-autoexec.so`**（均 patch 自原厂 `libAK8975.so`） |
| **preload 开关** | 让 hook 被系统加载 | `/etc/ld.so.preload` → 内容须与上面的 hook 路径一致 |
| **启动脚本** | 校验并解包胶片包、加载运行时 | `/tmp/autoexec.sh` |
| **胶片包** | 10 款胶片 + UI + worker + 抓拍守护 | `/tmp/a6400-film-boot-v15.tar` |

**关键认知（版本相关，重要）**：
- **V3.0 → V3.5.1**：hook 不变，升级只换"启动脚本 + 胶片包"两个文件。
- **V3.9 起结构变了**：hook 从 `/tmp` 迁到 `/etc`，且作者改为**每次从相机读库重新 patch 生成新 hook**，不再保留旧的。升级必须同步改 hook 与 preload 路径。
- 无论哪版，冷开机后若没菜单，九成是 hook 没被正确触发，而不是包坏了。

另有一个必须记住的触发条件：**V3 的菜单是 one-shot loader，编译初始态为 OFF**，开机后必须先做一次"手指触摸屏幕→松开"的自然事件，UI 才会挂到相机系统（`im.elf`）上。这正是 README 里"轻触屏幕并放开一次（必做）"的由来——不是可选项。

## 二、标准工作流程（六步）

### 步骤 1：开工前只读研究（不碰相机）
- 校验新包：`testzip()`、SHA256、manifest 与 tar 内各档哈希。
- 读 README 与部署脚本，重点看三处：**hook 检测逻辑**、**读库逻辑**、**上传逻辑**——这三处是历次翻车点。
- 判断用原版脚本还是补丁版：
  - hook 检测若还是"字符串子串匹配" → 复制脚本改判断为强制保留已验证 hook；
  - 作者若改了上传逻辑 → 一律改回成熟方案（见教训 2）。

### 步骤 2：确认起点 + 换驱动
- 确认相机在 mass storage 模式、电量充足，`D:` 可见。
- 用 Zadig 把 mass storage 设备换成 **libusb-win32**（作者脚本切换 service mode 需要它）。
- **装完立刻检查驱动包**：`pnputil /enum-drivers`，同一 `VID_054C&PID_0CA8` 只能有一个 `ilce-6400.inf` 包；多余的用 `pnputil /delete-driver oemXX.inf /uninstall /force` 删掉。`sony_a6400_service_mode.inf`（service mode 驱动）保留。
- 用 SCSI INQUIRY 测 bulk 通道确实可用（见教训 1 的判据）。

### 步骤 3：跑部署脚本
- 执行部署；成功标志因版本而异（`ONECLICK_V3_1_CLITE_DEPLOY_OK` / `ONECLICK_V3_5_1_FAST_SP_DEPLOY_OK` / V3.9 用自写脚本报告 `UPGRADE_V39_OK`）。
- **先判断 hook 策略**：V3.5.x 及以前可保留旧 hook；V3.9 必须重新生成并迁移到 `/etc`。
- 脚本正常或异常结束后，**相机通常停在 service mode**：若还要再连，必须物理重启（抠电池）回 mass storage。

### 步骤 4：验证写入（可选但推荐）
只读读回 `/tmp/autoexec.sh`、`/tmp/a6400-film-boot-v15.tar` 的 SHA256，与新包 manifest 比对；hook 哈希按版本核对（V3.9 应读到新路径 `/etc/a6400-autoexec.so` 且 preload 同步）。

### 步骤 5：还原驱动
```powershell
pnputil /remove-device "USB\VID_054C&PID_0CA8\<序列号>"
pnputil /delete-driver oemXX.inf /uninstall /force   # 删 mass storage 的 libusb 包
```
重新插拔后应回到 `usbstor.inf`、`D:` 可见。

### 步骤 6：冷开机验收
拔线 → 取电池 10 秒 → 开机等 35–40 秒 → **轻触屏幕松开一次** → 等 2 秒 → 长按 `MENU + 放大镜` 约 2 秒 → 检查新菜单项 → 开 LUT 拍照 → 查 `D:\A6400\TEST\F*.JPG`。

## 三、三条硬教训（最重要）

### 教训 1：Zadig 驱动包累积——最坑，表象极具迷惑性
Zadig 每次点 Replace Driver 都会**新建一个 `oemXX.inf` 且不删旧的**。同一 USB 设备累积多个 libusb 驱动包后，Windows 可能把设备绑定到配置不全的那个，表现为：

- **控制端点正常**（USB 描述符、厂商、序列号都能读到，设备管理器显示 OK）
- **bulk 端点超时**（PMCA 报 `libusb0-dll: _usb_reap_async timeout error`）

这看起来极像相机坏、数据线坏或电量不足——实测三者都不是。我在这上面浪费了十几轮。

**判据**（不依赖 PMCA，直接测 bulk）：发一个 31 字节 CBW 的 SCSI INQUIRY 到 EP `0x02`，从 EP `0x81` 读数据再读 13 字节 CSW。CSW 签名 `55534253` 且状态字节为 `00` 为健康。

**清法**：`pnputil /delete-driver oemXX.inf /uninstall /force` 删掉所有旧的 `ilce-6400.inf`(libusb-win32) 包，**只留一个**。换驱动 → 删旧包 → 重插，缺一不可。service mode 的 `oemNN.inf` 不要删。

### 教训 2：作者脚本的上传逻辑不稳——块数减半是解法
| 版本 | 作者原版上传 | 结果 | 自写方案 |
|---|---|---|---|
| V3.1 | 316 块 | — | 253 块成功 |
| V3.5.1 | 645 块 / 每块 3 行 echo / fast=True | 卡在 135、221 块；放宽超时+重试无效 | **515 块成功** |
| V3.9 | 1182 块 / 单命令 120 字符 + tmpfs + 盲目重试 | 改善到 1076/1182 才卡 | **591 块成功** |

- 病因：**累计回显导致终端 RC 标记无法匹配**，不是偶发抖动；块数越多越容易触发。
- **成熟方案**：`printf %s '<240字符块>' >> up.b64; echo __CKn__`，**每块独占一行确认标记**，收到确认再发下一块。同一 payload，块数比作者版减半。
- 注意：作者的 `retry_on_none` 是**盲目重试**（发 `\x03` 后重发同一条 `printf >>`）。若首写已落地只是 RC 丢失，重试会重复追加、损坏 base64。逐块确认比盲目重试安全。
- 推论：以后作者再改上传逻辑，直接用这套，不要先赌原版。

### 教训 3：PMCA 会话的后遗症
每次 PMCA service shell 会话结束后，相机停在 service mode；脚本**异常退出（traceback）也会卡住**。再连之前必须物理重启（抠电池）回 mass storage。连接前用 `pmca-console info` 确认出现 "camera in mass storage mode" 再跑脚本。

## 五、排错速查

| 现象 | 优先排查 |
|---|---|
| PMCA 找不到相机 / bulk timeout | ① 驱动包是否累积（教训 1）② 相机是否停在 service mode（教训 3） |
| 上传中途 `rc=None` | 作者上传逻辑（教训 2），换逐块确认脚本 |
| 部署报 OK 但没触屏菜单 | 检查 preload 与 hook 文件是否真的存在；"OK" 可能只代表包写入 |
| 菜单出不来但其他正常 | 是否漏了"轻触屏幕松开"触发动作（见第一节） |
| 拍照后没成品 | 看抓拍日志 `a6400-film-capture.runtime.log`：是否 baseline/元数据等待、是否有 disable 标记 |

## 七、给维护者的建议（已吸收合入主线）

1. 上传循环改回"每块独占行确认"；`retry_on_none` 的盲目重试有重复追加风险，应改为确认式重试。V3.9 的 1182 块在 1076 块仍卡，591 块方案可用。
2. README 补充：Windows 多次换驱动后应清理旧 `oemXX.inf`，否则会出现"相机看似死亡"的 bulk timeout。
3. 部署收尾在 tmpfs 仍挂载时 `rm -rf /tmp_bt/v39_up` 会报 `Device or resource busy`；先 `umount` 再删可让日志干净（非阻塞）。
