# V3.5.1 Fast SP 開發與架構細節

本文件彙整 **Sony ILCE-6400 (FW 2.00)** 自 **V3.1 CLite → V3.2 Universal → V3.4 Base LTR → V3.5 Fast → V3.5.1 Fast SP** 的實際硬體量測、瓶頸分析、記憶體／ABI 約束與安全性審查說明。

---

## 一、相機硬體真實規格與編譯限制

透過實機 `/proc/cpuinfo` 直接量測：

```text
Processor       : ARMv7 Processor rev 1 (v7l)
processor       : 0..3
Features        : swp half thumb fastmult vfp edsp vfpv3 vfpv3d16 tls vfpv4
CPU implementer : 0x41
CPU architecture: 7
CPU part        : 0xc05   (ARM Cortex-A5)
Hardware        : ARM-CXD900X0
```

- **重大結論：實機核心為 4 核 ARM Cortex-A5，不含 NEON SIMD (`neon` 不在 `Features` 內)**。
- 相機具備 `vfpv3-d16` 與 `vfpv4` 浮點，若錯誤啟用 `-mfpu=neon` 或手寫 NEON intrinsics，執行時將觸發 `SIGILL`。因此本專案一律採用 `-mcpu=cortex-a5 -mfpu=vfpv3-d16 -mfloat-abi=hard` 搭配純定點查表與迴圈重排最佳化。

## 二、效能調優全紀錄與各階段實機拆解

相機側完整記錄來源為 `FILM_TIMING` 與 `RAM_JOB_TIMING`（實測皆於 A6400 冷開機實拍所得）：

### 1. `6MP 高清 (3000×2000)` 演進：`33.41 s → 20.96 s → 17.49 s`

| 版本 | `decode_ms` | `film_ms` | `encode_ms` | `read→render` Shell 空檔 | `RAM_JOB_TIMING` 總耗時 | 關鍵技術原因 |
| --- | --- | --- | --- | --- | --- | --- |
| **V3.4 Base LTR** (`grain=2, halo=1`) | `22,315` | ~`2,000` | ~`5,000` | `~1,000+` | **`33,410 ms`** | 原版 `picojpeg` 逐 bit 解 Huffman + 6000×4000 全尺寸 IDCT 後才軟體降採樣 |
| **V3.5 Fast** (`grain=2, halo=1`) | `10,171` | `1,712` | `3,809` | `1,070 ms` | **`20,960 ms`** | 改寫 `vendor/picojpeg.c`（8-bit Huffman 快表 + `6MP` 半尺度 4×4→2×2 IDCT），直接省下 **12.45 秒** |
| **V3.5.1 Fast SP** (`grain=0, halo=0`) | **`9,828`** | **`574`** | **`3,144`** | **`50 ms`** | **`17,490 ms`** | 見下方 4 項針對性最佳化，再省 **3.47 秒** |

### 2. `1.7MP 極速 (1616×1080)` 演進：`8.16 s → 5.65~5.95 s`

- **V3.5 Fast**（`grain=2, halo=1`，`F9835789.JPG`）：`RAM_JOB_TIMING = 8,160 ms`（`WAITING → JOB_DONE = 8,860 ms`）。
- **V3.5.1 Fast SP**（`grain=0, halation=0`，`A6409839`、`A6409840`）：`RAM_JOB_TIMING = 5,950 ms` 與 **`5,650 ms`**（`WAITING → JOB_DONE = 6,359 ms`），`commit = 1,120 ~ 1,210 ms`。

### 3. V3.5.1 Fast SP 四項核心最佳化詳解

1. **`camera/film_ram_job.sh`：`ls -ln` 取代 `wc -c`（Shell 空檔 `1,070 ms → 50 ms`）**
   - 原版 `file_bytes()` 使用 `busybox wc -c < "$1"` 校驗讀取進 RAM 的原片大小；相機上精簡組態的 BusyBox（A6400 FW 2.00 實機為 `BusyBox v1.29.3 (2018-12-07)`，編入 `sha256sum`/`base64`，仍刻意避免 `printf` 等非共通選項）下，`wc -c` 會循序 `read()` 完整個 8–15 MiB 檔案，在 `tmpfs` 上造成約 1 秒多餘讀取延遲。
   - 改為單次 `lstat()` 呼叫：`$("$BB" ls -ln "$1")` 後取第 5 欄 `$5`（並維持純數字、`<= 8` 位數與 `EXPECTED_BYTES` 嚴格等長比對），將 `read → render` 空檔壓縮至 **`50 ms`**，同時移除渲染前重複的 `manifest` 與多餘 `post_native_guard`。
2. **`vendor/jpge.cpp` ＋ `-O3`（位元 100% 等價之編碼提速，`3,809 ms → 3,144 ms`）**
   - `camera/Makefile.film` 對 `jpge.o` 與 `author_film.o` 開啟 `-O3`。
   - `DCT_MUL(var, c)` 移除多餘 `static_cast<int16>` 符號擴展。
   - `quantize_pixels()` 合併正負分支並先以 `aj + (qi >> 1) < qi` 略過小於量化閾值係數的 64 位元乘法（减少指令快取壓力，在標準預設 `grain=2, halation=1` 下主機實測 `1.7MP` `bb3936f28b9a85a3225510d750167f25f857f79056dabb07758e7c4bff442745` 與 `6MP` `708edf698528f343fee796ac3c61bed9d94f6ce2de5d7d967528fb24bab305b9` **均與 V3.5 Fast 完全 SHA-256 位元一致**）。
   - 熱路徑 `put_bits()` 標記 `inline`，冷路徑 `flush_output_buffer()` 標記 `__attribute__((noinline))`。
3. **`camera/author_film.c`：預縮放粒子曲線 ＋ `O(1)` 滑動視窗模糊（`1,712 ms → 574 ms`）**
   - 進主迴圈前預計算 `bell_scaled[256] = grain_amp * film_grain_bell[i]`，省下逐像素雙重乘法。
   - `film_mask_blur` 水平方向（`radius=3`）由內層 `k = x-3..x+3` 重算總和改為左右滑動加減視窗（`s += mrow[x+3] - mrow[x-4]`）。
   - 當使用者於選單將 **底片光暈設為 `關閉`**（`halation=0`）時，Worker 完全不配置遮罩記憶體（`mask_kib=0`）並略過兩軸模糊與光暈合成。
4. **Thumb-2 指令集與 `a6400-film-boot-v15.tar <= 196,608 B` 體積預算控制**
   - `host-tests/build_film_capture_daemon.sh` 與 `host-tests/build_ui_trial3.sh` 採用 `-mthumb -Os` 搭配 `--gc-sections -Wl,-s`，使新增 `FILM_MENU_DETAILS` 與完整加速邏輯後的開機封裝包維持在 **`194,560 B`**（仍有 `~2 KiB` 安全餘裕）。

## 三、UI 架構、ABI 邊界與 1120-Byte 快照不變量

- **`_Static_assert(sizeof(ui) == 1120)` 不可打破**：
  - `a6400-film-menu-job.elf` 透過 `im.elf` 行程讀取 `ui.view.menu.settings`（位於 `struct a6400_ui_state` 開頭，偏移固定）。
  - 因此新增 UI 元素一律外掛於 `ui_theme`、`a6400_ui_toast_v1`（magic `0x54534f54`）與 `a6400_ui_hires_v1` 獨立符號，不改動 `ui` 本身 `1120 bytes` 與各核心欄位的 `offsetof()` 斷言。
- **主選單與子分頁觸控佈局（`640×480` 座標系）**：
  - `FILM_MENU_HOME`：4 列等高卡片列（`x=76..564`，`h=60`：`y=98` `LUT 濾鏡`、`y=168` `膠片風格`、`y=238` `膠片細節`、`y=308` 選用之 `快門聲`）＋ 底部左下 `畫質`（`x=76..340, y=386..428`, row ID `7`）＋ 右下 `關閉`（`x=404..564, y=386..428`, row ID `2`）。
  - `FILM_MENU_DETAILS`：3 列大按鈕（`顆粒強度`、`底片光暈`、`恢復細節預設`）＋ 右下 `返回`（row ID `5`）。在 `film_native_view_step()` 中只要觸發 `FILM_MENU_SETTINGS_CHANGED` 即重繪卡片，讓無改動 `stock` 的顆粒/光暈變更也能即時更新文字與高亮色塊。

## 四、動態掛勾、`manifest.json` 欄位語義與安全審查常見問答

### 1. 開機載入掛勾、休眠快照（`ssboot.bin`）與 `/tmp_bt` 觸發機制
- **為什麼必須開啟相機 Bluetooth，且為何服務模式下 `/tmp_bt` 不是 tmpfs？**
  - A6400 的核心架構透過 `/system/sabin/ssboot.bin`（`warm.mode=2`）從記憶體休眠快照直接喚醒主程式 `im.elf`（PID 149），因此 `im.elf` 與早期 `bootin.elf`（PID 142）在冷開機時**不經 `execve()` 與 `/lib/ld-2.11.2.so` `/etc/ld.so.preload`**。
  - 真正在正常開機後執行 `execve()` 的常駐元件為藍牙啟動鏈 **`startBTCore.sh → /usr/bin/bsa_server`**（開機約 14 秒啟動）：它會先掛載 **`none /tmp_bt tmpfs size=1024k`**，隨後執行 `/usr/bin/bsa_server` 觸發 `/etc/ld.so.preload` → `/tmp/a6400-autoexec.so`。
  - 若相機 **Bluetooth 關閉（或飛航模式開啟）**，或在未曾啟動藍牙的 USB 服務模式環境下檢視 `/tmp_bt`，它只會呈現為 `/dev/nflasha7`（唯讀且幾乎已滿的 8 MiB `ext2` rootfs）上尚未掛載的空目錄；此時手動 `remount,rw /` 並執行解包必然失敗（`No space left on device`）。請務必在相機端開啟 **Bluetooth 功能 = 開**（並維持 `/dev/nflasha7` 上的 `/tmp_bt` 為空目錄、勿在 `remount,rw` 後於 rootfs 殘留 `ae.lock`）。
- 針對未曾安裝過外掛的機身，部署腳本會從該機抽取 `/usr/lib/libAK8975.so`，驗證 ELF header、`.text == 0x988`、`.rodata` 不足重疊風險、`.dynamic` 尾部有連續兩格 `DT_NULL` 零值後，才植入 ARM `HOOK_STUB` 並寫入 `/tmp/a6400-autoexec.so`。
- `HOOK_STUB` 檢查 `/mnt/disable_hook`、`/mnt/disable.txt`、`/tmp/disable_hook` 與 `/tmp_bt/ae.lock`，並以獨立子行程在背景啟動 `/tmp/autoexec.sh`（開機 `bootstrap-local.sh` 嚴格限定 `native_sd_read=0`、`raw_sd_mount=0`，不讀寫 SD 卡、不呼叫 monitor）。

### 2. `manifest.json` 關鍵欄位解釋
- **`deployment_status: "BUILT_ONLY_NOT_INSTALLED"`**：由 `host-tests/build_film_local_boot_package.py` 於**編譯產生包體的當下**固定寫入（代表此建置器只組裝靜態套件、不會觸碰實體相機），**並非「未經實機測試」的標記**；實際版本是否冷開機驗證通過應對照 GitHub Release 說明與實測報告。
- **`template_pins` vs `files[]` / `bundle_entries[]`**：`template_pins` 記錄的是尚未替換當次 `package_id`、tar 位元組數與各執行檔 SHA-256 的原始 `.sh` 範本雜湊；實際部署與相機端 `bootstrap-local.sh` 檢驗完整性所依據的是 `files[]`、`extra_persistent_files[]` 與 `bundle_entries[]`。

### 3. SD 卡連拍寫尾競態保護個案（`A6409841.JPG`）
- 相機在連拍較大 JPEG 時，FAT/exFAT 目錄項目有時會先在 `MPR` 掃描露出一筆對齊 `64 KiB` 邊界的中間大小（實測個案：`8,388,608` bytes = `128 × 64 KiB`），於 `stb=500 ms` 後觸發 `IFSYS cp`，而相機於 `0.5~1s` 後才把最後一個 `64 KiB`（實卡最終 `8,454,144` bytes）flush 完成。
- 此時 `film_ram_job.sh` 讀取完畢後透過 `file_bytes` 比對 `8454144 != 8388608`，會立即在 **`stage=source_size`** Fail-Closed 中止寫回（耗時僅 `1,830 ms`）並觸發紅色 Toast，完全不會把不完整圖檔寫入 `/A6400/TEST/`，守護行程隨後繼續處理下一張照片 `A6409842.JPG`。
